# IPFAR 数据结构规范（草案）

> 定义 IPFS ↔ Arweave 桥的核心数据格式：Arweave Transaction Tags 标准 + 元数据 JSON 格式 + CAR v2 规范。

---

## 一、Arweave Transaction Tags

所有桥相关交易必须包含以下 Tags：

### 1.1 通用 Tags（所有桥交易必填）

| Tag 名 | Tag 值（Base64URL） | 说明 |
|--------|-------------------|------|
| `Protocol` | `IPFS-Arweave-Bridge` | 协议标识 |
| `Protocol-Version` | `1` | 协议版本 |
| `Content-Type` | `application/json` | 元数据 JSON（通过 `IPFAR-Type: meta` Tag 标识） |
| | `application/vnd.ipld.car` | CAR v2 文件（含 Index） |

### 1.3 元数据 Tags

当 `Content-Type` 为 `application/json` 且 `IPFAR-Type: meta` 时：

| Tag 名 | 说明 |
|--------|------|
| `IPFAR-Type` | `meta` — 标识此交易为元数据 |
| `Root-CID` | 根 CID（Base32 编码），用于搜索定位 |
| `Data-TXID` | 关联的 CAR 文件交易 ID（或 Bundle Item ID） |

### 1.4 CAR 文件 Tags

当 `Content-Type` 为 `application/vnd.ipld.car` 时：

| Tag 名 | 说明 |
|--------|------|
| `Root-CID` | 此 CAR 文件的根 CID（Base32） |
| `Data-Size` | 原始数据大小（字节） |
| `Reference` | 可选：`{"txid":{"height":1913001,"cids":["cid"]}}` |

## 二、元数据 JSON 格式

用于在 Arweave 上注册 CID → Arweave TX ID 的映射关系。

### 2.1 存储方式

- 单独发一笔交易，`Content-Type: application/json`，附加 `IPFAR-Type: meta` Tag
- `data` 字段为以下 JSON 的 **Base64URL 编码**

### 2.2 JSON 结构

```json
{
  "version": 1,
  "method": "raw",
  "root_cid": "bafy...",
  "data_txid": "arweave_tx_id",
  "data_height": 1913000,
  "data_size": 12345678,
  "reference": {
    "chunk_tx_id_1": {
      "height": 1913001,
      "cids": ["bafy...shared_root_cid_1", "bafy...shared_root_cid_2"]
    }
  },
  "content_type": "image/png",
  "original_name": "myfile.png"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `version` | int | ✅ | 元数据格式版本（当前为 1） |
| `method` | string | ✅ | 上传方式：`raw`（标准 Arweave 交易）/ `bundle`（ANS-104 Bundle） |
| `root_cid` | string | ✅ | 根 CID（Base32） |
| `data_txid` | string | ✅ | 主 CAR 文件所在 Arweave 交易 ID（Bundle 时为 Bundle Item ID） |
| `data_height` | int | ✅ | `data_txid` 所属区块高度 |
| `data_size` | int | ✅ | 原始数据大小（字节） |
| `reference` | object | 可选 | 引用映射：`{"txid": {"height": 1913001, "cids": ["cid1"]}}`。同时承担**数据去重**和**分块记录**两个功能 |
| `content_type` | string | 可选 | 原始内容的 MIME 类型 |
| `original_name` | string | 可选 | 原始文件名 |

## 三、CAR v2 文件格式

### 3.1 基本要求

- 格式：[CAR v2](https://ipld.io/specs/transport/car/carv2/)（必须含 Index）
- 根区块：对应 `Root-CID` 的 IPLD 根
- Index：必须包含所有区块的 CID→Offset 索引

### 3.2 上传方式

| 方法 | method 值 | 说明 |
|------|-----------|------|
| **原始交易** | `raw` | 标准 Arweave 交易。CAR 文件直接作为交易 data 通过 `POST /tx` 提交 |
| **ANS-104 Bundle** | `bundle` | 通过 Bundle 协议包装后上传。支持多 Item 打包、跨链兼容 |

两种方法均支持任意大小数据。大文件可通过分块机制拆分（见 §3.3）。

### 3.3 分块机制

当数据超过单笔交易限制时，将 DAG 拆分为多个独立 CAR v2 文件，通过 `reference` 字段记录分块关系：

```
大 IPLD DAG
  ├── CAR v2 主文件（含部分节点 + Index）→ data_txid 记录
  ├── CAR v2 分块1（含部分节点 + Index）→ reference 记录
  └── CAR v2 分块2（含部分节点 + Index）→ reference 记录
```

- 每个分块是**独立的 CAR v2 文件**（含完整 Index 和根 CID）
- `raw` 方式：每块独立为一笔 Arweave 交易
- `bundle` 方式：每块独立为一个 Bundle Item
- 主文件通过 `data_txid` 记录，分块文件通过 `reference` 字段记录（格式见 §4）
- 桥节点下载所有分块 → 合并为完整 DAG → 计算根 CID 验证
- 不分块时，`reference` 可省略
- 桥节点下载所有分块 → 合并为完整 DAG → 计算根 CID 验证
- 单块不分块时，`chunks` 可省略

### 3.4 验证要求

- 接收时必须验证 Index 正确性
- **无 Index 的 CAR v2 文件直接拒绝**

## 四、引用（Reference）

### 4.1 设计目标

`reference` 同时承担两个功能：
- **数据去重**：多个文件共享相同数据块时，通过引用避免重复上传
- **分块记录**：大文件拆分为多个 CAR 文件时，记录各分块的位置

### 4.2 引用格式

```json
{
  "reference": {
    "arweave_tx_id_chunk_1": {
      "height": 1913001,
      "cids": ["bafy...root_cid_1", "bafy...root_cid_2"]
    },
    "arweave_tx_id_chunk_2": {
      "height": 1913002,
      "cids": ["bafy...root_cid_3"]
    }
  }
}
```

每个引用的结构：

| 字段 | 说明 |
|------|------|
| key | 被引用的 Arweave 交易 ID（或 Bundle Item ID） |
| `height` | 该交易所属的区块高度，用于快速定位 |
| `cids` | 需要引用的 CID 列表（通常只填根 CID，树枝由 Index 覆盖） |

### 4.3 分块方式

当数据超过单笔交易限制时：
1. 将 DAG 拆分为多个独立 CAR v2 文件
2. 主文件通过 `data_txid` 记录，分块文件通过 `reference` 记录
3. 所有文件各自是完整的 CAR v2（含 Index 和根 CID）

### 4.4 引用粒度

- 可以引用另一个文件的**任意 CID**（不限于根 CID）
- 引用列表**只需填根 CID**——树枝由 CAR v2 Index 覆盖

### 4.5 传输与本地格式

| 层级 | 结构 | 说明 |
|------|------|------|
| 传输格式 | `{"txid": {"height": 1913001, "cids": ["cid", ...]}, ...}` | 紧凑，按文件分组 |
| 本地使用 | `{"cid": "txid", "cid": "txid", ...}` | 方便反向查询，可由传输格式转换生成 |

### 4.6 链式解析

由于引用是基于 CID 的，当被引用的文件自身也包含 `reference` 时，会自动形成递归链：

```
文件A.dedup_refs → 引用 文件B 的某个 CID
文件B.dedup_refs → 引用 文件C 的某个 CID

解析流程：
下载文件A → 发现 dedup_refs 引用 文件B 中的 CID → 下载文件B
  → 发现 dedup_refs 引用 文件C 中的 CID → 下载文件C
  → 回溯：文件C → 文件B → 文件A 组装完成
```

链式解析自动递归，无深度限制。

### 4.7 限制

- `Reference` 为**可选**功能
- 如果桥节点无法解析所有引用链，该文件标记为"不完整"

## 五、数据流总结

```
上传流程：
  原始数据 → 拆分（可选）→ 多个独立 CAR v2（含 Index）→ 分别上传 Arweave
  → 创建元数据 JSON（含 data_txid + dedup_refs 引用关系）→ 上传 Arweave

发现流程：
  GraphQL 搜索 Protocol Tag → 获取元数据交易
  → 解析 JSON → 获取 CAR 文件 TXID → 下载 CAR → 验证 Index

验证流程：
  下载 CAR v2 → 验证 Index → 计算 CID → 比对 Root-CID
  → 匹配 ✅ / 不匹配 ❌
```
